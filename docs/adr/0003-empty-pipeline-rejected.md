# 0003: Empty anchored pipeline rejected

- **Status:** Accepted
- **Date:** 2026-11-25
- **Supersedes (partially):** the empty-pipeline decision in
  `0002-resolve-grammar-inconsistencies.md` (its issue 2, plus the
  `START_OP '->' middleExpr? '->' END_OP` notation proposed for it). ADR-0002
  stays accepted for its remaining fixes (wildcard dual role, group
  quantifiers, single-element parens, interleaved imports).

## Context

ADR-0002 records "an empty pipeline is a valid query" and proposes
`START_OP '->' middleExpr? '->' END_OP` — an optional middle between the two
anchors. Two problems surfaced during implementation:

1. That notation cannot parse `start -> end` anyway: `middleExpr` regroups
   into `multipExpr` → `primary`, and a primary is required between the
   anchors (empirically: `extraneous input 'end'`). The interim grammar made
   `start -> end` legal via a dedicated two-term alternative, not the ADR
   notation.
2. Independent correctness review: an empty middle carries no query
   semantics. A pipeline anchored by `start` and `end` must contain at least
   one expression — `start -> end` is meaningless and should be rejected, not
   accepted.

## Decision

`start -> end` stays a parse error. The `patternExpr` rule keeps its
pre-Phase-2 shape — no empty-pipeline alternative, no optional middle:

```
patternExpr:
	START_OP '->' middleExpr '->' END_OP
	| START_OP '->' middleExpr
	| middleExpr '->' END_OP
	| middleExpr;
```

One-sided anchors (`start -> Q1`, `Q1 -> end`) and a bare middle expression
remain legal.

## Alternatives considered

- **Keep `start -> end` legal (ADR-0002's stance, interim implementation).**
  Rejected: an empty pipeline selects nothing useful and adds a grammar
  special case for no query value; the extra alternative also made
  `patternExpr` longer for a case no fixture or example uses.
- **Optional middle per ADR-0002's notation.** Rejected: unparseable as
  written; a `?` on the middle still leaves `start -> end` ambiguous between
  "valid" and "must be rejected" — the decision resolves this to rejected.

## Consequences

- **Positive:** the grammar has exactly one shape per anchor combination —
  every path from `start` to `end` contains at least one expression.
- **Positive:** ambiguous ADR notation is resolved by requiring the middle
  explicitly; tests pin `start -> end` as a parse error.
- **Neutral:** the README syntax reference documents the rule (the changelog
  is generated by `cz bump` and is not hand-edited).
- **Neutral:** no fixture or example depends on an empty pipeline.

## Confidence

High. The rejected notation was exercised against the generated parser; the
shipped rule is the exact pre-Phase-2 grammar that the fixture corpus already
covered.
